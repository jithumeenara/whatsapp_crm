# Reports പുതിയ രൂപകൽപ്പന: Business owner-നുള്ള പ്ലാൻ

തീയതി: 7 നവംബർ 2026. സ്ഥിതി: **പ്ലാൻ മാത്രം. ഒന്നും നിർമ്മിച്ചിട്ടില്ല, അംഗീകാരം കാത്തിരിക്കുന്നു.**

അടിസ്ഥാനം: നമ്മുടെ code വായിച്ചുള്ള പരിശോധന, മറ്റ് CRM-കളുടെ രേഖകൾ, AI report-കളെക്കുറിച്ചുള്ള ഗവേഷണം, ഒരു client-ന്റെ കൈകൊണ്ടുണ്ടാക്കിയ report-കൾ (മാതൃകയായി മാത്രം).

---

## 1. Owner ശരിക്കും ചോദിക്കുന്ന 5 ചോദ്യങ്ങൾ

ഓരോ സ്ക്രീനും ഈ ചോദ്യങ്ങളിൽ ഒന്നിന് ഉത്തരം നൽകണം. ഇല്ലെങ്കിൽ അത് ചേർക്കില്ല.

1. **എന്റെ പണത്തിന് ഫലം കിട്ടിയോ?** ചെലവ്, leads, നേടിയത്, വരുമാനം.
2. **Leads എന്തായി?** എത്ര വന്നു, എത്ര നേടി, എത്ര നഷ്ടപ്പെട്ടു, എത്ര ബാക്കി.
3. **എവിടെയാണ് leads ചോർന്നുപോകുന്നത്?** വിളിക്കാത്തവ, മറുപടി കിട്ടാത്തവ, മറന്ന follow-up.
4. **ഏത് agent-ന് എവിടെയാണ് സഹായം വേണ്ടത്?** എന്ത് ചെയ്താൽ മെച്ചപ്പെടും.
5. **ഈ ആഴ്ച ഞാൻ എന്ത് ചെയ്യണം?** എണ്ണമല്ല, 3 പ്രവൃത്തികൾ.

## 2. എവിടെയാണ് നമ്മൾ മുന്നിലെത്തുക

"എല്ലാ app-കളെക്കാളും മികച്ചത്" എന്ന് മുൻകൂട്ടി ഉറപ്പിക്കാൻ കഴിയില്ല. ഗവേഷണത്തിൽ കണ്ട ഒഴിവുകളിലാണ് നമ്മൾ ശ്രദ്ധിക്കുന്നത്. "കണ്ടെത്തിയില്ല" എന്നാൽ ആരും ചെയ്യുന്നില്ല എന്ന് ഉറപ്പല്ല.

| നമ്മുടെ മേൽക്കൈ | മറ്റുള്ളവർ | നമുക്ക് കഴിയുന്നതിന്റെ കാരണം |
|---|---|---|
| പരസ്യച്ചെലവ് → പരസ്യം → lead → നേടിയ തുക → agent, ഒറ്റ report-ൽ | പരിശോധിച്ച രേഖകളിൽ ഈ മുഴുവൻ ശൃംഖല കണ്ടില്ല | Chat, lead, agent, പരസ്യം എല്ലാം നമ്മുടെ കൈയിൽ |
| ചോർച്ച പട്ടിക: ഓരോ വരിയും അമർത്തിയാൽ ആ lead തുറക്കും | മിക്കവയും എണ്ണം മാത്രം | Lead, chat, follow-up ഒരേ സ്ഥലത്ത് |
| "നാളെ വിളിക്കാം" എന്ന വാഗ്ദാനം പാലിച്ചോ | വാഗ്ദാനം കണ്ടെത്തൽ ഉണ്ട് (Gong), പാലിച്ചോ എന്ന പരിശോധന കണ്ടില്ല | ശേഷമുള്ള message, call, task നമുക്ക് കാണാം |
| Lost reason, chat-ലെ തെളിവ് സഹിതം | Chatfuel ഭാഗികമായി; മറ്റുള്ളവർ agent എഴുതുന്നത് മാത്രം | മുഴുവൻ chat നമ്മുടെ കൈയിൽ |
| ആഴ്ചതോറും WhatsApp-ൽ 3 പ്രവൃത്തികൾ | കണ്ടെത്തിയില്ല; സാധാരണ email PDF മാത്രം | WhatsApp അയക്കൽ ഇപ്പോൾ തന്നെയുണ്ട് |
| ക്രമീകരണം ഇല്ലാതെ, ഏത് വ്യവസായത്തിനും | വലിയ CRM-കളിൽ report ഉണ്ടാക്കാൻ പഠിക്കണം | ഉണ്ടാക്കേണ്ട, തയ്യാറായി കിട്ടും |

## 3. ആദ്യം അറിയേണ്ട സത്യം: ഇപ്പോഴത്തെ കണക്കുകൾ മുഴുവൻ വിശ്വസനീയമല്ല

## 4. ഏത് വ്യവസായത്തിനും ചേരുന്ന രീതി

**Funnel ഓരോ business-നും സ്വന്തം.** ഓരോ ഘട്ടവും Open, Won, Lost എന്നതിൽ ഒന്നിലേക്ക് ചേരും. Zoho, HubSpot ഉപയോഗിക്കുന്നതും ഇതേ രീതിയാണ്.

| വ്യവസായം | ഘട്ടങ്ങൾ (തുടക്കം, മാറ്റാം) |
|---|---|
| ആശുപത്രി | Appointment → Visited → Procedure/Surgery (Won) |
| പരിശീലനം, വിദ്യാഭ്യാസം | Enquiry → Registered → Attended (Won) |
| Real estate | Site visit → Booking (Won) |
| Retail, service | Quote → Order (Won) |
| ഒന്നും തിരഞ്ഞെടുത്തില്ലെങ്കിൽ | Contacted → Won |

- **സംഭരണം:** `LeadSettings`-ൽ `funnel_stages` എന്ന പട്ടിക. Lead-ൽ "ഘട്ടം മാർക്ക് ചെയ്യുക" ബട്ടൺ, അത് `LeadActivity`-യിൽ രേഖപ്പെടുത്തും.
- **`Lead.status` മാറ്റമില്ല:** അത് ജോലിയുടെ അവസ്ഥയായി തുടരും, അതിനാൽ ഇപ്പോഴത്തെ Leads സ്ക്രീനുകൾ തകരില്ല.
- **ഘട്ടം ഒഴിവാക്കിയാൽ:** "ഒരിക്കലെങ്കിലും എത്തിയ" leads ആണ് എണ്ണുക. HubSpot-ൽ ഘട്ടം ഒഴിവാക്കിയാൽ funnel തെറ്റുന്നു എന്ന പരാതിയുണ്ട്.
- **വ്യവസായ പേരുകൾ code-ൽ ഇല്ല:** templates ഡാറ്റയായി മാത്രം.

**"എന്തിനെക്കുറിച്ച്" എന്ന തരംതിരിവ്** (മാതൃകയിലെ TKR, Varicose പോലെ): നിലവിലുള്ള `ServiceCategory` ഉപയോഗിക്കും. Lead-ലേക്ക് ഒരു ബന്ധം ചേർക്കണം. ആശുപത്രിക്ക് ചികിത്സ, പരിശീലനത്തിന് programme, കടയ്ക്ക് product.

**Lost reason:** ഓരോ business-നും സ്വന്തം പട്ടികയിൽ നിന്ന് തിരഞ്ഞെടുക്കണം, "മറ്റുള്ളവ" അനുവദിക്കും. വെറും free text ആയാൽ എണ്ണാൻ കഴിയില്ല.

### Pipeline തുക: Deal-ൽ (user തീരുമാനിച്ചു, 7 നവംബർ)

**തുക തീരുമാനിക്കുന്നത് lead-ൽ അല്ല, Pipelines-ലെ Deal-ലാണ്.** Lead എണ്ണത്തിനും (വന്നത്, നേടിയത്, നഷ്ടപ്പെട്ടത്) Deal പണത്തിനും.

| Deal-ന്റെ ഘട്ടം (`stage_type`) | Report-ൽ |
|---|---|
| Open | **Pipeline തുക** (Open deals-ന്റെ `value` ആകെ) |
| Won | **നേടിയ വരുമാനം** |
| Lost | **നഷ്ടപ്പെട്ട തുക** |

- **തരംതിരിവ്:** Pipeline, ഘട്ടം, deal-ന്റെ agent (`Deal.assigned_to`), lead-ന്റെ source, category, പരസ്യം (`Deal.lead_id` വഴി).
- **തുക 0 ആയ deals:** വരുമാനമായി കൂട്ടില്ല. "30 deals, 22 എണ്ണത്തിന് തുകയുണ്ട്" എന്ന് പറയും.
- **Deal ഇല്ലാത്ത leads:** എണ്ണത്തിൽ വരും, പണത്തിൽ വരില്ല. "Won leads-ൽ X എണ്ണത്തിന് deal ഇല്ല" എന്ന് report കാണിക്കും.
- **ആദ്യം ലളിതമായ ആകെ.** Weighted രീതി Phase 6-ൽ, സ്വന്തം ചരിത്രം മതിയാകുമ്പോൾ.

**ഇതിനായി Deal-ൽ ശരിയാക്കേണ്ടത് (Phase 0):**
- `won_at`, `lost_at`, `lost_reason`, `closed_by` ഇല്ല. ഇപ്പോൾ എപ്പോൾ നേടി എന്ന് അറിയാൻ കഴിയില്ല.
- `status`-ഉം ഘട്ടത്തിന്റെ `stage_type`-ഉം ഒരുമിച്ച് മാറണം. ഒന്നിൽ നിന്ന് മാത്രം കണക്കാക്കും.
- ഘട്ട മാറ്റങ്ങളുടെ ചരിത്രം ഇപ്പോൾ audit log-ൽ മാത്രം. Report-ന് ഒരു deal ചരിത്രം വേണം.
- Currency സാധാരണ USD ആണ്. Business-ന്റെ currency ആക്കണം. പഴയ deals തൊടില്ല, കാണിക്കുമ്പോൾ currency പറയും.
- Lead close ചെയ്യുമ്പോൾ ഉണ്ടാക്കുന്ന deal-ന് തുക അയക്കുന്നില്ല, അതിനാൽ 0 (`leads/[id]/page.tsx:396`). തുക ചോദിക്കണം.
- Lead-ൽ നിന്ന് close-ന് മുമ്പേ "Pipeline-ലേക്ക് ചേർക്കുക" ബട്ടൺ. ഇല്ലെങ്കിൽ open pipeline എപ്പോഴും ശൂന്യമായിരിക്കും.
- Deal-ൽ എന്ത് ഉണ്ടെന്ന് (എത്ര deals, എത്രയ്ക്ക് തുക) ഓരോ server-ലും എണ്ണം മാത്രം നോക്കും.

### Report settings: Settings-ൽ പ്രത്യേക ഭാഗം (user ആവശ്യപ്പെട്ടത്)

Settings → **Reports** (admin, owner മാത്രം). Leads settings-ൽ നിന്ന് വേറിട്ട്. ഉള്ളടക്കം:

1. Funnel ഘട്ടങ്ങൾ: പേര്, ക്രമം, Open/Won/Lost, വ്യവസായ template.
2. തുക: Deal-ന് തുക നിർബന്ധമാണോ, currency, report ഏത് pipeline-കൾ എണ്ണണം.
3. ചോർച്ച പരിധികൾ: എത്ര സമയം കഴിഞ്ഞാൽ "മറുപടി കിട്ടിയില്ല".
4. Digest: ആർക്ക്, ഏത് ദിവസം, ഏത് സമയം.
5. കൈകൊണ്ടുള്ള പരസ്യച്ചെലവ്.
6. AI സഹായം: ഓൺ/ഓഫ് (Phase 5 വന്ന ശേഷം).

ഇത് ഇല്ലെങ്കിലും report പ്രവർത്തിക്കണം: എല്ലാത്തിനും സാധാരണ മൂല്യങ്ങൾ.

## 5. അടിസ്ഥാന നിയമങ്ങൾ (AI ഉണ്ടെങ്കിലും ഇല്ലെങ്കിലും)

1. **ഒരു കണക്കിന് ഒരു നിർവചനം:** `src/lib/reports/metrics.ts`-ൽ എല്ലാ കണക്കും, അർത്ഥം സ്ക്രീനിൽ കാണിക്കും. ഓരോ സ്ക്രീനും ഇതിൽ നിന്നേ എടുക്കൂ.
2. **ഓരോ സംഖ്യയും അമർത്താം:** അതിന് പിന്നിലെ leads-ന്റെ പട്ടിക തുറക്കും.
3. **കണക്ക് പൊരുത്തപ്പെടണം:** Won + Lost + ഫലമില്ല + Open = ആകെ. ഇത് test ഉറപ്പാക്കും. പൊരുത്തപ്പെടാത്തപ്പോൾ കാരണം സ്ക്രീനിൽ പറയും.
4. **രണ്ട് കാഴ്ചകൾ, വ്യക്തമായ പേരോടെ:**
   - *ഈ കാലയളവിൽ വന്ന leads എന്തായി* (cohort): പ്രധാന കാഴ്ച, കൂട്ടിയാൽ ആകെ കിട്ടും.
   - *ഈ കാലയളവിൽ നടന്ന പ്രവൃത്തികൾ:* പഴയ lead ഈ ആഴ്ച നേടിയതും ഇതിൽ വരും.
5. **ന്യായമായ താരതമ്യം:** മാസത്തിന്റെ 10 ദിവസത്തെ കഴിഞ്ഞ മാസത്തിന്റെ ആദ്യ 10 ദിവസവുമായി മാത്രം.
6. **Business സമയം:** `businessTimezone`, `dayStartIso`. Server സമയം ഒരിക്കലും ഇല്ല.
7. **ചെറിയ എണ്ണം:** 10 leads-ൽ 3 എന്നത് 30% എന്ന് വലുതായി കാണിക്കില്ല. മങ്ങിച്ച്, എണ്ണം സഹിതം. 10-ൽ 3-ന്റെ യഥാർത്ഥ പരിധി ഏകദേശം 7–65% ആണ്.
8. **പഴയ കണക്ക്:** Phase 0-ന് ശേഷം മാത്രം കൃത്യമാകുന്നവയ്ക്ക് "ഈ തീയതി മുതൽ" എന്ന് കാണിക്കും. പഴയത് ഊഹിക്കില്ല.
9. **വ്യക്തിഗത വിവരം:** Report-ൽ സംഖ്യകൾ മാത്രം. Export-ഉം drill-down-ഉം അനുമതി നോക്കും, audit log-ൽ രേഖപ്പെടുത്തും.

## 6. നിർമ്മാണ ഘട്ടങ്ങൾ

### Phase 0: കണക്ക് ശരിയാക്കൽ (AI ഇല്ല, എല്ലാത്തിനും മുമ്പ്)

- **ബഗുകൾ:** ഭാഗം 3-ലെ won/lost പിഴവുകൾ. ആദ്യം പരാജയപ്പെടുന്ന test, പിന്നെ fix.
- **Migration 158** (രണ്ടുതവണ ഓടിച്ചാലും സുരക്ഷിതം, ആദ്യം പകർപ്പിൽ):
  - `deals`: `won_at`, `lost_at`, `lost_reason`, `closed_by`; deal ഘട്ട ചരിത്രം (പുതിയ table)
  - `leads`: `closed_by`, `first_response_at`, `first_response_by`, `lost_reason_key`, `ad_id`, `whatsapp_config_id`, `service_category_key`
  - `lead_settings`: `funnel_stages`, `report_settings`
  - സൂചികകൾ: `lead_activities (account_id, created_at)`, leads-ൽ `converted_at`, `lost_at`. Index ഉണ്ടാക്കുമ്പോൾ table പൂട്ടാം, അതിനാൽ തിരക്ക് കുറഞ്ഞ സമയത്ത്.
- **Call:** ഓരോ ഫലത്തിനും `type: 'call'` activity, status മാറിയില്ലെങ്കിലും. Connected ആയോ എന്നും.
- **Status മാറ്റങ്ങൾ:** bulk, webhook ഉൾപ്പെടെ എല്ലായിടത്തും ഒരേ helper.
- **Close dialog:** സാധാരണ Won മാറ്റും. Pipeline-ലേക്ക് ചേർക്കുമ്പോൾ deal തുക ചോദിക്കും. Lost reason പട്ടികയിൽ നിന്ന്.
- **പരിശോധന:** ഓരോ server-ലും ഈ fields എത്ര നിറഞ്ഞിട്ടുണ്ട് എന്ന് എണ്ണം മാത്രം നോക്കും.

### Phase 1: Owner report (AI ഇല്ല)

`/reports` പേജ്. ഒരു സ്ക്രീൻ, ക്രമീകരണം ഒന്നും വേണ്ട. മൊബൈലിൽ ആദ്യം.

1. **ഒറ്റ വാചകം:** "ഈ ആഴ്ച 160 leads വന്നു, 12 നേടി, 40 പേരെ ഇനിയും വിളിച്ചിട്ടില്ല." Code എഴുതുന്നത്, AI അല്ല.
2. **കാലയളവ്:** ഇന്ന്, ആഴ്ച, മാസം, സ്വന്തം തീയതി.
3. **6 സംഖ്യകൾ, കഴിഞ്ഞ കാലയളവുമായി താരതമ്യം:** Leads, Won, Lost, Pending, നേടിയ വരുമാനം, Pipeline തുക.
4. **Funnel:** Business-ന്റെ സ്വന്തം ഘട്ടങ്ങൾ.
5. **ചോർച്ച പട്ടിക:** ഒരിക്കലും വിളിക്കാത്ത leads, സമയം കഴിഞ്ഞിട്ടും മറുപടിയില്ലാത്ത chat-കൾ, വൈകിയ follow-up, ആരുടെയും പേരിലില്ലാത്ത leads. ഓരോ വരിയും തുറക്കാം.
6. **തരംതിരിവ്:** Source, category, നമ്പർ/channel. Lost reason കൂട്ടങ്ങൾ.
7. **മറുപടി വേഗം × വിജയം:** Business-ന്റെ സ്വന്തം ഡാറ്റയിൽ നിന്ന് ("5 മിനിറ്റിനുള്ളിൽ മറുപടി നൽകിയവയിൽ X% നേടി"). പുറത്തെ benchmark ലക്ഷ്യമായി കാണിക്കില്ല.
8. **Excel export, print/PDF:** `safeText`, business സമയം. Slides-നുള്ള PPT പിന്നീട് (Phase 6).

നിറം പ്രശ്നങ്ങൾക്ക് മാത്രം. ഒന്നും പ്രശ്നമില്ലെങ്കിൽ "ഈ ആഴ്ച ചോർച്ചയില്ല" എന്ന്.

### Phase 2: Agent report (AI ഇല്ല)

റാങ്ക് പട്ടികയല്ല, **"ഇവിടെ സഹായം വേണം, ഇത് ചെയ്യാം"** എന്നതാണ് രൂപം.

- **കണക്കുകൾ:** വിളികൾ, connected %, leads, നേടിയത്, നഷ്ടപ്പെട്ടത്, conversion, മറുപടി വേഗം, വൈകിയ follow-up, leads-ന്റെ ഓരോ ഘട്ടം.
- **ന്യായം:**
  - മറുപടി സമയം assign ചെയ്തത് മുതൽ, ജോലി സമയത്ത് മാത്രം, bot ഒഴിവാക്കി.
  - Conversion ഒരേ source-ൽ ഉള്ളവരുമായി താരതമ്യം. പരസ്യ leads കിട്ടുന്നയാൾ മികച്ചവനാകണമെന്നില്ല.
  - Owner-ന്റെ കാഴ്ചയിൽ മാത്രം ടീമിന്റെ സ്വന്തം ശരാശരിയുമായി താരതമ്യം.
  - ചെറിയ എണ്ണം മങ്ങിക്കും.
  - Credit നിയമം സ്ക്രീനിൽ: വിജയം അടച്ചയാൾക്ക് (`closed_by`).
- **സാധാരണ പരിശോധന (AI ഇല്ല):** "Connected എന്ന് രേഖപ്പെടുത്തി, പക്ഷേ call-ഉം message-ഉം കാണുന്നില്ല". എഴുത്ത് എപ്പോഴും "പരിശോധിക്കുക", ഒരിക്കലും "കള്ളം" അല്ല. ഫോണിൽ നേരിട്ട് വിളിച്ചാൽ app അറിയില്ല.
- **Agent-ന് സ്വന്തം കണക്ക് മാത്രം (തീരുമാനിച്ചു).** മറ്റൊരാളുടെ പേര്, സംഖ്യ, റാങ്ക്, ടീം ശരാശരി ഒന്നും കാണില്ല. Export-ഉം ഇല്ല. ഇത് browser-ൽ മറച്ചാൽ പോരാ, server തന്നെ agent-ന്റെ വരി മാത്രം നൽകണം; ഒരു agent മറ്റൊരാളുടെ id കൊടുത്താലും കിട്ടരുത്, test നിർബന്ധം. Supervisor, admin, owner എന്നിവർക്ക് ടീം മുഴുവൻ. എന്തൊക്കെ അളക്കുന്നു എന്ന് എല്ലാവരെയും അറിയിക്കണം.
- **ഇപ്പോൾ ഇല്ല:** ഒറ്റ സ്കോർ, idle time, എല്ലാവർക്കും കാണുന്ന leaderboard.

### Phase 3: പണവും പരസ്യവും (AI ഇല്ല)

- **ദിവസേന ചെലവ്:** പുതിയ table, `level=ad` Insights. അവസാന 28 ദിവസം വീണ്ടും എടുക്കും, കാരണം Meta കണക്ക് അത്രയും ദിവസം മാറാം.
- **Lead ↔ പരസ്യം:** WhatsApp-ലെ `source_id` വഴി (`ctwa_clid` അല്ല, Status പരസ്യങ്ങളിൽ അത് ഇല്ല). Lead form-ന് `ad_id`.
- **Report:** പരസ്യം/campaign → ചെലവ് → leads → നേടിയത് → വരുമാനം → ROI. ബന്ധമില്ലാത്ത leads പ്രത്യേക വരിയിൽ.
- **കൈകൊണ്ട് ചെലവ്:** Google, പത്രം, Meta connect ചെയ്യാത്തവർ. Kommo ചെയ്യുന്ന രീതി.
- **Payment:** Contact തലത്തിലുള്ള ബന്ധം മാത്രം, അതിനാൽ "ഏകദേശം" എന്ന് പറയും.
- **ഒറ്റ ശൃംഖല:** ഏത് പരസ്യത്തിൽ നിന്ന് വന്ന lead ഏത് agent നേടി. ഇതാണ് നമ്മുടെ പ്രധാന മേൽക്കൈ.
- **പരിശോധിക്കാനുള്ളത്:** Token-ന് `ads_read` ഉണ്ടോ; ad account timezone business timezone തന്നെയോ; `referral` ആദ്യ message-ൽ മാത്രമാണോ.

### Phase 4: Owner-ന്റെ കൈയിൽ എത്തിക്കൽ (AI ഇല്ല)

- **ആഴ്ചയിലൊരിക്കൽ WhatsApp digest:** സംഖ്യകളും code തിരഞ്ഞെടുത്ത 3 പ്രവൃത്തികളും ഒരു link-ഉം. `brief-sweep` ഉപയോഗിക്കും. 24 മണിക്കൂർ കഴിഞ്ഞാൽ approved template വേണം.
- **Email digest:** ഇപ്പോൾ ഇല്ല, ചേർക്കണം.
- **മുന്നറിയിപ്പ്:** "ഇന്ന് 10 leads ആരും വിളിച്ചില്ല" പോലുള്ളവ. പ്രശ്നമില്ലെങ്കിൽ നിശ്ശബ്ദം.
- **സുരക്ഷ:** Digest-ൽ customer നമ്പറോ പേരോ ഇല്ല. Link തുറക്കാൻ login വേണം. ലഭിക്കുന്നയാളുടെ അനുമതി അനുസരിച്ചുള്ള ഡാറ്റ മാത്രം.
- **സമയം:** ദിവസം അടഞ്ഞ ശേഷം അയക്കും, "ഈ സമയം വരെ" എന്ന് കാണിക്കും.

### Phase 5: AI ഭാഗം (business തിരഞ്ഞെടുത്താൽ മാത്രം)

**ഇരുമ്പ് നിയമം:** സംഖ്യകൾ code കണക്കാക്കും, AI വാക്കുകൾ മാത്രം എഴുതും. Code നൽകാത്ത സംഖ്യ AI പറഞ്ഞാൽ ആ മറുപടി തള്ളും.

കാരണം: AI സ്വന്തമായി SQL ഉണ്ടാക്കുന്ന രീതിയിൽ നല്ല സാഹചര്യത്തിൽ പോലും ഏകദേശം മൂന്നിലൊന്ന് തെറ്റി (പഠനം). Agent സ്കോറിംഗിൽ പ്രോംപ്റ്റിലെ പഴയ വിവരം കാരണം സ്കോർ മാറുന്നതും കണ്ടിട്ടുണ്ട്.

| ക്രമം | Feature | എങ്ങനെ | അപകടം, പരിഹാരം |
|---|---|---|---|
| 1 | Digest എഴുത്ത് | Code നൽകിയ വസ്തുതകൾ മലയാളത്തിൽ/ഇംഗ്ലീഷിൽ ഭംഗിയാക്കും | പരാജയപ്പെട്ടാൽ Phase 4 template |

| 5 | Script അനുസരിച്ച് coaching | ഓരോ കണ്ടെത്തലിനും chat-ലെ വാക്ക്, അപ്പീൽ ബട്ടൺ, കൈകൊണ്ടുള്ള പരിശോധന | പഠിക്കാൻ മാത്രം. ശമ്പളത്തിനോ ശിക്ഷയ്ക്കോ ഒരിക്കലും |

**തുടങ്ങുന്നതിന് മുമ്പ്:**
- **അളക്കൽ:** യഥാർത്ഥ chat-കളിൽ നിന്ന് കൈകൊണ്ട് അടയാളപ്പെടുത്തിയ ഒരു test set, മലയാളവും Manglish-ഉം ഉൾപ്പെടെ. ഈ കൃത്യത ആരും പ്രസിദ്ധീകരിച്ചതായി കണ്ടില്ല, അതിനാൽ നമ്മൾ തന്നെ അളക്കണം.
- **ശബ്ദം:** Call voice വിശകലനം ഇപ്പോൾ ഇല്ല. മലയാളം transcription ഇപ്പോഴും ദുർബലമാണ്.
- **ചെലവ്:** ഓരോ business-നും പരിധി. ഇപ്പോഴത്തെ AI വില ഉറപ്പിക്കാൻ കഴിഞ്ഞില്ല, ആദ്യം അളക്കും.

**സ്വകാര്യത:**
- സാധാരണ **ഓഫ്**. Business തന്നെ ഓണാക്കണം.
- ആശുപത്രികളിൽ chat വിശകലനം ഓഫ് തന്നെ. ഓണാക്കിയാലും നമ്പറുകൾ മറച്ച്, ചികിത്സാ chat ഒഴിവാക്കി.
- Paid AI key മാത്രം. Gemini-യുടെ free tier-ൽ വ്യക്തിഗത ഡാറ്റ അയക്കരുതെന്ന് Google തന്നെ പറയുന്നു.
- Customer-നുള്ള notice-ൽ "AI വിശകലനം" പറയണം. Agent-മാരെയും അറിയിക്കണം.
- DPDP ചുമതലകൾ ഏകദേശം മെയ് 2027 മുതൽ തുടങ്ങും. ഈ ഭാഗം അഭിഭാഷകൻ പരിശോധിക്കണം. ആശുപത്രി ഡാറ്റ ഇന്ത്യയിൽ തന്നെ നിൽക്കണമോ എന്നതും.

### Phase 6: പിന്നീട്

PPT/PDF "CEO pack", weighted pipeline തുക (സ്വന്തം ചരിത്രത്തിൽ നിന്ന്), Meta-ലേക്ക് won അയക്കൽ (Conversions API, App Review വേണം), നഷ്ട വരുമാന ഏകദേശ കണക്ക് (business-ന്റെ സ്വന്തം ചരിത്രം ഉണ്ടെങ്കിൽ, "ഏകദേശം" എന്ന് എഴുതി).

## 7. ഇപ്പോൾ നിർമ്മിക്കാത്തത്

1. സ്വന്തമായി report ഉണ്ടാക്കുന്ന builder. അത് owner-ന് വേണ്ട, ഒരു "22-widget" പരാതിയിലേക്ക് എത്തിക്കും.

3. ഒറ്റ agent സ്കോർ, ശമ്പളവുമായോ ശിക്ഷയുമായോ ബന്ധിപ്പിച്ചത്.
4. വിജയ സാധ്യത പ്രവചനം. ചെറിയ business-ന് ഡാറ്റ പോരാ.

6. Multi-touch attribution.
7. പുറത്തെ benchmark ലക്ഷ്യമായി കാണിക്കൽ.
8. മാതൃകയിലെ creative status പോലുള്ളവ. അത് agency-യുടെ ജോലിയാണ്, CRM report അല്ല.

## 8. സാങ്കേതിക കുറിപ്പുകൾ

- **API:** `requirePageAccess('/reports', 'supervisor')`. Agent-ന് സ്വന്തം വരി മാത്രം (`performance/route.ts:50` പോലെ). `account_id` എല്ലായിടത്തും.
- **Reuse:** `lib/leads/outcome.ts`, `api/leads/funnel`, `conversion-funnel.tsx`, `api/broadcasts/[id]/export` (Excel), `brief-sweep.ts`, `staff-alert.ts`, `lib/audit/zoned.ts`.
- **ഉപയോഗിക്കരുത്:** `call-action-panel.tsx`, `close-enquiry-dialog.tsx` (പേജുകൾ ഉപയോഗിക്കുന്നില്ലെന്ന് തോന്നുന്നു).
- **വേഗം:** ആദ്യം നേരിട്ടുള്ള query + സൂചികകൾ + ചെറിയ cache. മന്ദഗതിയായാൽ മാത്രം ദിവസേനയുള്ള സംഗ്രഹ table.
- **`server.ts` import:** Digest sweep-ൽ `next/server` വരരുത്.
- **Index സൂക്ഷ്മത:** Schema-യിൽ ഇല്ലാത്ത index-കൾ `prisma db push` കളയാം. Migration വഴി മാത്രം.
- **പരിശോധന:** ഓരോ കണക്കിനും test, പൊരുത്ത test, 360px, `crm-ui-review`, ഒരു ലോഗിൻ-ചെയ്ത ഉപയോക്താവിനെക്കൊണ്ടുള്ള Playwright click-through.
- **Audit:** Export-ഉം digest settings-ഉം audit log-ൽ. `coverage.test.ts` പുതിയ routes പരിശോധിക്കും.

## 9. വിജയം എങ്ങനെ അളക്കും

- **30 സെക്കൻഡ് പരിശോധന:** ഒരു owner-ന് സഹായം ഇല്ലാതെ 5 ചോദ്യങ്ങൾക്കും ഉത്തരം കിട്ടണം.
- **ഒരു മാസം സമാന്തരമായി:** ആശുപത്രി client-ന്റെ കൈകൊണ്ടുള്ള report-ഉം നമ്മുടെ report-ഉം ഒത്തുനോക്കും. വ്യത്യാസങ്ങൾക്ക് കാരണം കണ്ടെത്തും.
- **കൈവേല:** അവരുടെ report തയ്യാറാക്കാനുള്ള സമയം കുറയണം.
- **ഉപയോഗം:** Owner ആഴ്ചതോറും തുറക്കുന്നുണ്ടോ, ചോർച്ച പട്ടിക കുറയുന്നുണ്ടോ.
